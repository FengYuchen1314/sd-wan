# PathWeaver 最终设计方案

## 1. 目标与边界

PathWeaver 由任意数量的对等节点组成。所有设备运行同一套安装包，均提供完整 Web 面板、Agent、制品转发和 WireGuard 数据面；安装时不再选择“中心”或“边缘”。首台无加入令牌的设备自动成为当前配置协调节点，后续设备使用令牌加入。协调节点只是内部串行化数据库写入的实现细节，不是用户选择的部署角色。

每台设备的面板默认监听 TCP `19773`，安装时必须交互输入本机密码。密码只在本机使用带随机盐的 scrypt 摘要保存，不随配置传播。普通节点面板通过 Agent 的现有无环控制路径把 API 请求实时送到当前配置协调节点，因此所有面板读取和修改的是同一份版本化配置。协调节点把经过校验的 SQLite 逻辑快照同步到选民多数派；副本只用于故障接管，不在多个 SQLite 上并发写入。完全单向节点的面板请求由管理父节点轮询取走、执行并带回结果，这类节点不参加协调选举。

系统不会自动建立最短路径或局域网直连。用户定义的拓扑是数据流量的唯一合法路径。任何成功保存的拓扑必须保证节点组内所有有效业务 IP 两两可达。

## 2. 控制面与数据面

每个节点运行统一节点服务，并维护两个逻辑 WireGuard 接口：

- `pw-control`：节点身份、心跳、面板请求、命令和配置传递。首次加入形成一棵稳定的接入树；不能直达协调节点时，由已验证邻接逐跳转发。
- `pw-data`：用户业务流量。业务 IP、Peer 邻接和转发路径可以在面板修改。

控制树与数据拓扑分离，确保修改业务 IP 或数据路径时不会丢失管理能力。控制父节点也允许通过独立的“迁移控制上游”操作安全变更，但数据拓扑编辑不会隐式修改控制树。

## 3. 节点接入

### 3.1 主动加入

管理员在任意节点面板选择节点组、接入节点以及新设备可访问的地址和控制端口。选择后，面板从节点记录自动填充协议、地址和端口，也允许仅为本次接入覆盖。系统生成短时效的一次性加入令牌；命令不携带新节点自己的监听端口或面板密码。新节点从所选接入节点下载统一节点包，在本机交互选择端口并设置密码，注册后建立控制通路，本机面板立即可用。

安装文件允许逐级缓存和传递，但信任根始终是集群签名，转发节点不能修改制品。

### 3.2 被动认领

无法主动连接任何已入网节点的服务器固定从 `FengYuchen1314/sd-wan` 的 `main` 分支下载同一套节点包，并使用认领令牌进入监听状态；本机仍启动完整面板。管理员在任意面板指定一个能访问目标的已入网节点，再填写目标 IP 和控制端口。认领方主动连接目标、验证令牌并代目标完成注册。

认领完成后不会要求目标反向连接父节点。发起节点保存一个只绑定该目标的管理会话，持续主动请求目标：代报心跳、代取期望配置、把配置和节点命令推送给目标，再把执行结果上报中心。目标只响应由父节点发起的连接。数据面的初始 WireGuard Endpoint 也只配置在主动侧；被动侧通过主动侧发起的握手学习对端地址。发起节点成为默认控制父节点，首次数据连接仍严格对应这条认领路径。

被认领节点仍可作为下一台设备的认领方。若它自身也是单向受管节点，认领请求、面板请求和后续控制消息会沿已有代理路径逐级封装转发；每一跳只主动连接自己的直接下级，配置协调节点不会绕过初始控制拓扑直连更深层节点。

## 4. 数据拓扑模型

数据拓扑是带方向角色的连接图。每条连接记录“上游节点”和“下游节点”，但 WireGuard Peer 本身支持双向数据传输。方向用于表达管理意图、拓扑展示和路径约束。

一个节点可以拥有多个允许的上游和多个下游。配置协调服务根据已启用连接计算确定性的逐目的节点路径：

1. 只使用面板声明的连接；
2. 优先级数字更小的连接优先；
3. 同优先级按稳定节点 ID 排序；
4. 为每个源节点和目标业务 `/32` 计算下一跳；
5. 为直连 Peer 生成无重叠的 `AllowedIPs`；
6. 禁止 Agent 自行发现或创建额外 Peer。

保存前必须验证：无重复业务 IP、无自连接、引用节点有效、所有节点属于同一节点组，并且把连接视为可双向传输后图完全连通。未来的必经/禁行策略可作为路径约束层加入，不改变基础模型。

### 4.1 可视化连接工作流

拓扑页面根据当前 active、preparing 和 probing 连接运行确定性的力导向布局。连接变化时未固定节点会自动重新收敛；管理员拖动过的节点作为固定点保留。画布支持拖动平移以及 `Ctrl + 滚轮` 围绕指针缩放。管理员可直接点选两个未连接节点，并填写至少一个方向的可达地址：“节点 A 可被节点 B 访问的 IP/域名”或“节点 B 可被节点 A 访问的 IP/域名”；两个地址都填时才探测双向。双方 WireGuard 端口从节点记录自动回填，并允许在本次连接中单独覆盖。

新连接不会立即参与路由，而是依次经历：

1. 中心校验节点身份、地址格式、重复连接和候选拓扑；
2. 两端 Agent 接收同一个短时探测凭据并准备探测入口；
3. 仅对管理员已填写的方向下发主动访问命令；探测 HTTP 端口从节点数据库读取，WireGuard 端口也从节点记录自动回填并允许本次覆盖；
4. 验证期间画布显示虚线，失败显示错误线且不改变现网；
5. A→B 或 B→A 任一方向成功即可转为 active；所有已填写方向都失败才拒绝建链，成功方向会单独记录；
6. 中心重新计算全网下一跳，仅为探测成功方向保留 WireGuard Endpoint；未填写或失败方向不生成 Endpoint，然后发布新配置版本。

单向可达并不要求被访问端能够反向连接发起端。例如上海节点经日本 NAT 主动访问伦敦时，只在上海侧写入伦敦 Endpoint，伦敦侧保持无 Endpoint。配置激活后，持有 Endpoint 的 Agent 会立即向对端业务 IP 发送一次预热数据包，促使 WireGuard 发起握手并建立 NAT 映射；后续 `PersistentKeepalive` 维持该映射。TCP 控制探测只负责确认“哪一边能够主动到达”，实际数据面健康仍以 WireGuard 握手为准。

每次连通性探测都携带不可复用的探测 ID、已访问节点轨迹和剩余跳数，默认最多 16 跳并受请求超时约束。Agent 拒绝重复探测 ID、轨迹中再次出现自己的请求以及耗尽跳数的请求；控制中继也会追加并检查独立的转发轨迹，因此后期拓扑形成环时会快速失败，不会无限递归转发。

### 4.2 默认线路、故障切换与负载均衡

选中两个节点后可进入独立路径详情页。中心只在 active 连接图上枚举简单路径：一条路径内的节点不可重复，因此不会绕环；同一个真实节点允许出现在多条路径中，界面会在每条路径泳道中重复绘制它。为防止稠密图导致组合爆炸，结果按成本、跳数和稳定节点 ID 排序并限制返回数量。

每个节点对支持两种互斥策略：

- **默认线路与故障切换**：管理员选择一条默认线路，其余无环路径按成本成为候选线路。Agent 汇报相邻 WireGuard 握手健康度；默认线路包含失效连接时，中心选择第一条不包含已知故障连接的候选路径、生成新配置版本并协同切换整条逐跳路由。恢复后的旧线路不会自动抢回主路径，避免来回抖动。
- **加权策略**：管理员选择至少两条路径，并为每条路径设置 `1..1000` 的整数权重。节点对、路径序列、连接序列和权重保存到 `path_policies`，两个端点收到方向相反但权重相同的 `multipathPolicies`。控制器从控制网段为每条路径分配一对不会与节点地址冲突的端点别名，并逐跳把这些 `/32` 写入对应 WireGuard Peer 的 `AllowedIPs`。Linux Agent 在 `pw-data` 上为每个活动成员创建独立 IPIP 隧道，把策略接管的目的网段安装成按连接哈希选择的加权 ECMP 路由。Agent 最多每 20 秒读取一次相邻 WireGuard 握手状态；任一路径包含已确认故障的连接时，协调服务保留原权重、把运行时有效权重置为 `0` 并生成新版本，隧道和 ECMP 成员随版本原子重建，恢复后按原权重加入。

没有显式路径策略的普通拓扑同样使用握手健康结果：连接确认故障后，配置编译器先从基础图中排除该连接并重新计算逐跳路由。故障连接仍以不携带 `AllowedIPs` 的健康探测 Peer 留在两端配置中，因此不会继续承载业务流量，但有 Endpoint 的一侧会继续用 keepalive 复检；握手恢复后生成新版本并重新把连接加入基础拓扑。如果排除故障连接会让拓扑完全断开，则保留原配置并报告故障，不会虚构面板未声明的路径。

默认线路与故障切换会直接重编译逐跳 `AllowedIPs`。加权模式用路径专属 IPIP 隧道区分同一 WireGuard 邻接上的不同端到端线路，并把用户权重按比例归一化到 Linux nexthop 的 `1..256` 范围；原始权重仍保存在数据库和面板中。安装器同时启用 IPv4 转发，并把反向路径过滤设为 loose 模式，以允许合法的多路径回程。

### 4.3 安全删除节点

当前配置协调节点在协调权迁移完成前不可删除。删除其他节点前，控制器会在内存中移除该节点及其所有相邻连接，再对剩余节点执行全网可达性编译；只要任一业务 IP 会失联，面板就弹出受影响节点警告并拒绝删除。仍承担单向认领代理的节点也必须先迁移其下级。

### 4.4 节点端口分配

统一安装脚本不询问角色。每台设备从 TCP `19773` 探测面板端口、从 UDP `19801` 探测 WireGuard 端口；加入现有网络的设备还从 TCP `8790` 探测控制中继端口。直接回车采用首个空闲端口；手动输入的端口若被占用会要求重新输入。面板密码必须交互输入两次且至少 8 个字符，生成的加入命令不会携带密码。

### 4.5 内置 WireGuard 运行时

PathWeaver 不调用宿主机 PATH 中已有的 `wg` 或 `wg-quick`。配置协调服务固定 WireGuard Tools 版本和 SHA-256，并在首次请求时从官方源码仓库拉取、校验和缓存；任意接入节点可继续转发该制品。节点安装脚本每次运行都会重新编译到 `/opt/pathweaver-agent/runtime/wireguard-<version>-<install-id>`。

Linux 内核中的 WireGuard 驱动属于操作系统网络能力，不等同于宿主机安装的管理工具。所有节点通过同一私有运行时准备、检查和激活配置，系统原有 WireGuard 工具、配置和其他接口不会被覆盖。

### 4.6 业务网段变更

业务网段只能完整位于 RFC 1918 私有范围。面板先检查与控制网段、其他节点组网段的重叠及地址容量，并展示节点地址重分配预览。当前在线节点在准备阶段检查本机接口及路由占用；任一在线节点失败时保留原网段和原地址。离线节点被标记为延后，不会让配置永久停在 preparing；它恢复后通过稳定控制路径直接追赶最新 active 版本。

## 5. IP 与拓扑变更事务

业务 IP 和数据拓扑均通过不可变配置版本发布：

1. **计算**：当前配置协调服务在数据库事务内构建期望状态并验证全网可达性；
2. **预下发**：新版本沿当前控制树逐级送达相关 Agent；
3. **准备**：Agent 校验 WireGuard、路由、端口和本机环境，只写临时配置；
4. **激活**：所有必要节点准备成功后，协调服务下发激活阶段；
5. **验证**：Agent 汇报握手与路由探测结果；
6. **完成**：新版本成为 active，之后才清理旧 Peer/旧 IP；
7. **回滚**：超时或失败时恢复上一 active 版本。

配置版本会记录发布时必须确认的在线节点以及延后的离线节点。在线节点在发布过程中掉线超过心跳期限后转为延后，剩余在线节点完成两阶段提交即可激活；延后节点恢复时仍必须在本机完成同样的冲突检查和激活流程。

业务 IP 变更以稳定 Node ID 为对象，并同步更新所有节点的路由、`AllowedIPs`、ACL 和名称记录。切换窗口内可暂时保留旧 IP，减少不同节点激活时间差造成的黑洞。

## 6. 控制协议

节点 API 分为三类：

- `/api/v1/*`：面板 API，本机使用安装密码验证；非协调节点通过 Agent 实时转发；
- `/agent/v1/*`：Agent 注册、心跳、配置状态和命令队列；
- `/relay/v1/*`：父节点转发子节点控制请求，端到端携带节点凭据。

普通 Agent 主动轮询，因此节点无需接受来自协调服务的公网入站连接。每个配置版本记录节点到当前协调节点以及全部选民的受限数量无环控制路径；Agent 每次请求随机排列这些路径，面板 API、心跳、快照复制和选举消息复用同一套路径、轨迹检查与 16 跳上限。

严格单向的被认领 Agent 仍由父节点主动轮询，父节点代理其中心 API 通信；目标不建立反向控制连接。父节点自身访问中心时同样使用上述动态无环路径，因此固定的只有最后一段父节点到被认领目标的单向会话。父节点也能为普通下级提供安装脚本、制品缓存和控制请求中继。

## 7. 安全模型

- WireGuard 私钥只在本机生成和保存；配置数据库仅保存公钥。
- 加入令牌保存为 SHA-256 摘要，具有节点组、父节点、模式、时效和次数限制。
- 每个 Agent 获得独立随机凭据，配置数据库只保存摘要。
- WireGuard Tools 使用固定版本与 SHA-256 校验；应用节点包当前依赖 HTTPS 或可信内网传递，尚未实现独立的离线签名验证。
- 每台设备的面板密码使用随机盐 scrypt 摘要保存；节点间面板代理另用仅限回环地址的随机凭据。
- 所有 IP、拓扑、认领、迁移和密钥操作写入审计日志。
- Agent 仅执行白名单命令，并以最小化能力运行；网络配置步骤单独使用受控提权。

## 8. 高可用与故障行为

系统始终只有一个持有写租约的配置协调节点，并使用 SQLite WAL 串行化事务。每项导致审计修订号变化的 HTTP 写入会在向用户确认成功前，把带版本号和外键校验的逻辑快照同步到变更前选民集合的多数派。严格单向受管节点不投票；普通可中继节点是稳定选民。协调心跳租约为 12 秒，失联后候选节点随机退避、递增任期，并且只有快照版本不落后且获得多数票的节点才能启动本机协调服务。新协调节点创建新的全网配置版本；旧节点收到更高任期后立即停止本机协调服务，恢复上线的旧初始节点会导入新快照并把面板请求沿无环路径转发给新协调节点。

单节点的多数派是自身，可以独立读写。双节点的多数派为两台，因此其中一台失联时系统保留现有数据隧道和只读状态，但拒绝配置写入，避免网络分区形成双主。要在单节点故障后自动继续写入，需要至少 3 个能够通过已验证控制路径互通的普通节点；3 节点集群可在任意 1 个选民故障时由其余 2 个完成接管。

数据拓扑可以包含冗余连接。默认线路失效时，协调服务会在管理员允许的无环候选路径中自动切换；加权策略中的故障路径会从 Linux ECMP 活动成员暂时移除并每 20 秒复检，恢复后使用保存的权重重新加入。如果所有候选均包含已知故障连接，则保留当前策略并报告失败，不会越过面板声明的连接，也不会无限尝试环路。

## 9. 组件边界

- `src/center`：当前配置协调服务、SQLite 逻辑快照、编排和配置发布。
- `src/peer`：每个普通节点上的完整静态面板与实时 API 代理。
- `src/core`：IPv4/CIDR、拓扑验证、路径计算和节点配置编译。
- `src/agent`：注册、轮询、配置准备/激活、WireGuard 与路由适配。
- `public`：所有节点共用的管理面板。
- `scripts`：Linux 安装和服务部署脚本。
- `deploy`：systemd 与生产部署样例。

## 10. 交付阶段

当前仓库已包含控制服务、全节点面板、Agent 协议、拓扑编译、被动认领、两阶段发布、Linux WireGuard/IPIP/ECMP 数据面以及多数派协调迁移。后续生产增强项包括 RBAC、审计导出、应用制品离线签名和分批升级回滚。
