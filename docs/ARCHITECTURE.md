# PathWeaver 最终设计方案

## 1. 目标与边界

PathWeaver 由一台具有公网入口的中心服务器和任意数量的边缘节点组成。中心承载 Web 面板、控制 API、配置数据库、安装文件和中心 WireGuard 节点。边缘节点可以没有公网地址，只要它能主动连接一个已入网节点，或者能被一个已入网节点连接。

系统不会自动建立最短路径或局域网直连。用户定义的拓扑是数据流量的唯一合法路径。任何成功保存的拓扑必须保证节点组内所有有效业务 IP 两两可达。

## 2. 控制面与数据面

每个节点运行统一 Agent，并维护两个逻辑 WireGuard 接口：

- `pw-control`：节点身份、心跳、命令和配置传递。首次加入形成一棵稳定的接入树。子节点不能直接访问中心时，由父节点转发控制请求。
- `pw-data`：用户业务流量。业务 IP、Peer 邻接和转发路径可以在面板修改。

控制树与数据拓扑分离，确保修改业务 IP 或数据路径时不会丢失管理能力。控制父节点也允许通过独立的“迁移控制上游”操作安全变更，但数据拓扑编辑不会隐式修改控制树。

## 3. 节点接入

### 3.1 主动加入

管理员在面板选择节点组、控制父节点以及新节点可访问的父节点地址和控制端口。选择父节点后，面板从节点记录自动填充协议、地址和端口，也允许仅为本次接入覆盖。中心生成短时效、一次性的加入令牌和安装命令；命令不携带新节点自己的监听端口。新节点从中心或父节点下载同一套 Agent，在本机交互选择空闲端口，注册后建立父子控制隧道。

安装文件允许逐级缓存和传递，但信任根始终是中心签名，边缘节点不能修改制品。

### 3.2 被动认领

无法主动连接任何已入网节点的服务器固定从 `FengYuchen1314/sd-wan` 的 `main` 分支下载统一安装脚本和基础 Agent，并使用认领令牌进入监听状态；WireGuard 官方源码仍执行固定 SHA-256 校验。管理员在面板指定一个能访问目标的已入网节点，再填写该节点实际能够访问的目标 IP 和控制端口。认领命令沿已有控制树发送到发起节点，由发起节点主动连接目标、验证令牌并代目标向中心注册。

认领完成后不会要求目标反向连接父节点。发起节点保存一个只绑定该目标的管理会话，持续主动请求目标：代报心跳、代取期望配置、把配置和节点命令推送给目标，再把执行结果上报中心。目标只响应由父节点发起的连接。数据面的初始 WireGuard Endpoint 也只配置在主动侧；被动侧通过主动侧发起的握手学习对端地址。发起节点成为默认控制父节点，首次数据连接仍严格对应这条认领路径。

被认领节点仍可作为下一台设备的认领方。若它自身也是单向受管节点，认领请求和后续控制消息会沿已有代理路径逐级封装转发；每一跳只主动连接自己的直接下级，中心不会绕过初始控制拓扑直连更深层节点。

## 4. 数据拓扑模型

数据拓扑是带方向角色的连接图。每条连接记录“上游节点”和“下游节点”，但 WireGuard Peer 本身支持双向数据传输。方向用于表达管理意图、拓扑展示和路径约束。

一个节点可以拥有多个允许的上游和多个下游。中心根据已启用连接计算确定性的逐目的节点路径：

1. 只使用面板声明的连接；
2. 优先级数字更小的连接优先；
3. 同优先级按稳定节点 ID 排序；
4. 为每个源节点和目标业务 `/32` 计算下一跳；
5. 为直连 Peer 生成无重叠的 `AllowedIPs`；
6. 禁止 Agent 自行发现或创建额外 Peer。

保存前必须验证：无重复业务 IP、无自连接、引用节点有效、所有节点属于同一节点组，并且把连接视为可双向传输后图完全连通。未来的必经/禁行策略可作为路径约束层加入，不改变基础模型。

### 4.1 可视化连接工作流

拓扑页面根据当前 active、preparing 和 probing 连接运行确定性的力导向布局。连接变化时未固定节点会自动重新收敛；管理员拖动过的节点作为固定点保留。画布支持拖动平移以及 `Ctrl + 滚轮` 围绕指针缩放。管理员可直接点选两个未连接节点，并分别填写“节点 A 可被节点 B 访问的 IP/域名”和“节点 B 可被节点 A 访问的 IP/域名”。双方 WireGuard 端口从节点记录自动回填，并允许在本次连接中单独覆盖。

新连接不会立即参与路由，而是依次经历：

1. 中心校验节点身份、地址格式、重复连接和候选拓扑；
2. 两端 Agent 接收同一个短时探测凭据并准备探测入口；
3. 两端 Agent 分别从管理员填写的地址主动访问对方，探测 HTTP 端口从节点数据库读取，WireGuard 端口也从节点记录自动回填并允许本次覆盖；
4. 验证期间画布显示虚线，失败显示错误线且不改变现网；
5. A→B 或 B→A 任一方向成功即可转为 active；两个方向都失败才拒绝建链，成功方向会单独记录；
6. 中心重新计算全网下一跳，为该连接使用双方填写的 WireGuard Endpoint，并发布新配置版本。

每次双向探测都携带不可复用的探测 ID、已访问节点轨迹和剩余跳数，默认最多 16 跳并受请求超时约束。Agent 拒绝重复探测 ID、轨迹中再次出现自己的请求以及耗尽跳数的请求；控制中继也会追加并检查独立的转发轨迹，因此后期拓扑形成环时会快速失败，不会无限递归转发。

### 4.2 默认线路、故障切换与负载均衡

选中两个节点后可进入独立路径详情页。中心只在 active 连接图上枚举简单路径：一条路径内的节点不可重复，因此不会绕环；同一个真实节点允许出现在多条路径中，界面会在每条路径泳道中重复绘制它。为防止稠密图导致组合爆炸，结果按成本、跳数和稳定节点 ID 排序并限制返回数量。

每个节点对支持两种互斥策略：

- **默认线路与故障切换**：管理员选择一条默认线路，其余无环路径按成本成为候选线路。Agent 汇报相邻 WireGuard 握手健康度；默认线路包含失效连接时，中心选择第一条不包含已知故障连接的候选路径、生成新配置版本并协同切换整条逐跳路由。恢复后的旧线路不会自动抢回主路径，避免来回抖动。
- **负载均衡**：管理员选择至少两条路径，并为每条路径设置 `1..1000` 的整数权重。节点对、路径序列、连接序列和权重保存到 `path_policies`，两个端点收到方向相反但权重相同的 `multipathPolicies`。Agent 最多每 20 秒读取一次相邻 WireGuard 握手状态；任一路径包含已确认故障的连接时，中心保留它的配置权重、把运行时有效权重置为 `0` 并生成新版本。只有收到明确的 `reachable` 恢复报告后才按原权重自动加回，启动宽限期内的 `unknown` 不会误清除故障。

默认线路与故障切换会直接重编译逐跳 `AllowedIPs`。真正的数据面加权并发分流仍需要把每个物理邻接映射为独立 WireGuard 接口或等价的可区分隧道，再由 Linux 策略路由按连接哈希选择接口；控制器已经下发完成该适配所需的路径与权重元数据。

### 4.3 安全删除节点

中心节点不可删除。删除其他节点前，控制器会在内存中移除该节点及其所有相邻连接，再对剩余节点执行全网可达性编译；只要任一业务 IP 会失联，面板就弹出受影响节点警告并拒绝删除。仍承担被动认领认证代理的节点也必须先迁移其下级。通过预检后，相关路径策略会失效、控制父引用会迁回中心，并生成新的不可变配置版本。

### 4.4 节点端口分配

WireGuard 监听端口是节点属性，不再假设全网所有节点共用一个端口。统一安装脚本先询问中心或边缘角色。中心节点从 TCP `8787` 探测面板/节点接入端口、从 UDP `19801` 探测 WireGuard 端口；边缘节点从 TCP `8790` 探测控制中继端口、从 UDP `19801` 探测 WireGuard 端口。直接回车采用首个空闲端口；手动输入的端口若被占用会要求重新输入。最终端口由节点注册和心跳写入数据库，面板生成的加入命令只包含父节点入口，不替新节点决定端口。

### 4.5 内置 WireGuard 运行时

PathWeaver 不调用宿主机 PATH 中已有的 `wg` 或 `wg-quick`。中心固定 WireGuard Tools 版本和 SHA-256，并在首次请求时从官方源码仓库拉取、校验和缓存；边缘父节点可继续转发该制品。节点安装脚本每次运行都会重新编译到 `/opt/pathweaver-agent/runtime/wireguard-<version>-<install-id>`，写入 PathWeaver 运行时清单，再把 `wireguard-current` 切换到这次安装。Agent 只执行该目录中的绝对路径，并把配置保存在自己的数据目录。

Linux 内核中的 WireGuard 驱动属于操作系统网络能力，不等同于宿主机安装的管理工具。PathWeaver 无论宿主机是否已有 `wg`，都会下载固定版本源码、校验摘要并构建自己的 `wg`/`wg-quick` 运行时。边缘节点使用独立的 `pw-data` 接口；中心为每个节点组使用独立接口。中心和边缘都通过这套运行时准备、检查和激活配置，系统原有 WireGuard 工具、配置和其他接口不会被覆盖。当前部署基线要求内核已支持 WireGuard。

### 4.6 业务网段变更

业务网段只能完整位于 RFC 1918 私有范围。面板先检查与控制网段、其他节点组网段的重叠及地址容量，并展示节点地址重分配预览。确认发布后，候选网段和地址只写入待发布配置，不立即覆盖权威数据；中心和所有边缘节点在准备阶段检查本机接口及路由占用。任一节点失败时保留原网段和原地址，只有全部节点准备并激活成功后才提交数据库切换。

## 5. IP 与拓扑变更事务

业务 IP 和数据拓扑均通过不可变配置版本发布：

1. **计算**：中心在数据库事务内构建期望状态并验证全网可达性；
2. **预下发**：新版本沿当前控制树逐级送达相关 Agent；
3. **准备**：Agent 校验 WireGuard、路由、端口和本机环境，只写临时配置；
4. **激活**：所有必要节点准备成功后，中心下发激活阶段；
5. **验证**：Agent 汇报握手与路由探测结果；
6. **完成**：新版本成为 active，之后才清理旧 Peer/旧 IP；
7. **回滚**：超时或失败时恢复上一 active 版本。

业务 IP 变更以稳定 Node ID 为对象，并同步更新所有节点的路由、`AllowedIPs`、ACL 和名称记录。切换窗口内可暂时保留旧 IP，减少不同节点激活时间差造成的黑洞。

## 6. 控制协议

中心 API 分为三类：

- `/api/v1/*`：管理员 API，使用管理令牌或后续的登录会话；
- `/agent/v1/*`：Agent 注册、心跳、配置状态和命令队列；
- `/relay/v1/*`：父节点转发子节点控制请求，端到端携带节点凭据。

普通 Agent 主动轮询，因此边缘节点无需接受来自中心的公网入站连接。每个配置版本记录节点到中心的所有受限数量无环控制路径；Agent 每次请求随机排列这些路径，单条路径失败后在同一个总超时预算内尝试下一条。路径头携带剩余节点、已访问轨迹和最多 16 跳上限，中继只接受数据库中已验证的直接邻居作为下一跳，因此既不会在环中递归，也不能被利用为任意 HTTP 代理。配置响应沿成功请求原连接返回，相当于下发路径也随每次轮询动态变化。

严格单向的被认领 Agent 仍由父节点主动轮询，父节点代理其中心 API 通信；目标不建立反向控制连接。父节点自身访问中心时同样使用上述动态无环路径，因此固定的只有最后一段父节点到被认领目标的单向会话。父节点也能为普通下级提供安装脚本、制品缓存和控制请求中继。

## 7. 安全模型

- WireGuard 私钥只在本机生成和保存；中心仅保存公钥。
- 加入令牌保存为 SHA-256 摘要，具有节点组、父节点、模式、时效和次数限制。
- 每个 Agent 获得独立随机凭据，中心只保存摘要。
- 安装制品使用中心离线签名密钥签名，Agent 固定信任公钥并验证哈希。
- 管理面板生产环境强制 HTTPS、强管理令牌，并预留 OIDC/MFA/RBAC。
- 所有 IP、拓扑、认领、迁移和密钥操作写入审计日志。
- Agent 仅执行白名单命令，并以最小化能力运行；网络配置步骤单独使用受控提权。

## 8. 高可用与故障行为

首版中心为单实例，SQLite 采用 WAL。控制树中的父节点故障会影响其子树接收新配置；已激活的数据隧道继续工作。后续版本增加中心热备、控制父节点备选和制品多副本。

数据拓扑可以包含冗余连接。默认线路失效时，中心会在管理员允许的无环候选路径中自动切换；加权策略中的故障路径会暂时退出活动成员并每 20 秒复检，恢复后使用保存的权重重新加入。如果所有候选均包含已知故障连接，则保留当前策略并报告失败，不会越过面板声明的连接，也不会无限尝试环路。

## 9. 组件边界

- `src/center`：HTTP 服务、持久化、认证、编排和配置发布。
- `src/core`：IPv4/CIDR、拓扑验证、路径计算和节点配置编译。
- `src/agent`：注册、轮询、配置准备/激活、WireGuard 与路由适配。
- `public`：嵌入中心服务的管理面板。
- `scripts`：Linux 安装和服务部署脚本。
- `deploy`：systemd 与生产部署样例。

## 10. 交付阶段

1. 可运行控制器、面板、Agent 协议和配置编译器；
2. Linux 上真实 WireGuard 双平面应用、父节点 HTTP 中继和制品签名；
3. 被动认领、两阶段自动推进与主动探测；
4. 中心高可用、备用控制上游、RBAC、审计导出和升级回滚。
